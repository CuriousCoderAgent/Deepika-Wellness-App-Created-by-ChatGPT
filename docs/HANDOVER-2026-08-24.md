## 2. Shared contracts that changed — read before building on them

Per §4 of the coordination note: communicate `MemberDoc`/API/env changes
before the other stream builds on them. Here is everything since `fad7644`.

### `Member` (both `lib/types.ts` and `mobile/src/types.ts`)

```ts
onboardedAt?: string;
```

Set the first time onboarding's `finish()` runs. Not decorative — the server
now derives `member.week`/`member.phase` from it on every read
(`lib/day-offset.ts`'s `programWeek()`, called from `rebaseMemberDoc()`,
which already runs inside `lib/db.ts` for every `readMemberDoc` /
`readAllMemberDocs`). Before this, `week` was set once at signup and nothing
anywhere ever advanced it — every real member was permanently on "Week 1."
If iOS onboarding has its own `finish()`-equivalent, or constructs a member
document some other way, it needs to stamp this field too or the same bug
recurs on that path specifically.

`programWeek()` returns `null` — not `1` — when `onboardedAt` is absent, and
`rebaseMemberDoc()` leaves `member.week`/`phase` untouched in that case. So
this is safe to leave unset on a document you're not ready to wire up yet;
it will just keep behaving exactly as before.

### `Message`

```ts
from: "coach" | "member" | "system" | "ai";
```

New variant, not a replacement. `"ai"` is Vera (below) — kept distinct from
`"coach"` so a human is never impersonated. If iOS has its own message-bubble
rendering, it needs a case for `"ai"` or those messages render however your
`default`/fallback case currently handles an unrecognised `from`.

### `mobile/src/types.ts` only

```ts
coaching?: { mode: "none" | "coached"; ownedDomains?: ActionDomain[] };
```

Mirrors what already existed server-side; the mobile type just didn't have it
before. Read-only from the client either way — nothing writes it from mobile.

### New route: `POST /api/coach/ask`

Vera — see §3. Auth and error shape match the rest of `app/api/**`: bearer
token, 401/403 the same way, never a 500 (an unreachable model returns a
normal 200 with an "I can't reach my side of things" reply rather than an
error the client has to handle specially).

### New env var: `OPENAI_COACH_MODEL`

Same pattern as the three existing `OPENAI_*_MODEL` vars — falls back to
`"gpt-5"` if unset, which this account's key can't see, so the route degrades
to the same "unavailable" reply rather than failing loudly. **Already set on
Vercel** (Eshan did this directly), so production is live. Add it to your own
`.env.local` if you run the coach route locally.

## 3. Vera — a second AI surface, same safety doctrine as the plan generator

The Coach tab used to be a message box nothing answered — a human coach is a
paid extra almost nobody has. It now has an AI coach, Vera, grounded in the
member's real state (today's plan, readiness outcome, recent effort,
check-ins) and bounded the same way the rest of this product is: **rules
decide, models phrase**, enforced in three places rather than trusted to a
system prompt —

1. **Before the model** — `lib/coach-ai.ts`'s `matchUrgent()` catches
   emergency language by pattern (chest pain, breathlessness at rest,
   one-sided weakness, heavy bleeding in pregnancy, suicidal ideation,
   throat closing) and answers from fixed text, no network call. Works when
   the model is down, when the key is missing, whatever else is in the
   message. `matchRefusal()` does the same for diagnosis/dosing questions.
2. **In the instructions** — given her real numbers, told to repeat them and
   never invent others.
3. **After the model** — `sanitiseReply()` replaces (not edits) any reply
   containing sets/reps/kilos or a false claim to have changed the plan.

Vera has no route that writes `doseSteps`, `pausedExerciseIds`, `coaching`
or the readiness outcome. Nothing about this needs an iOS-specific
counterpart beyond rendering `from: "ai"` bubbles (§2) — the safety logic is
entirely server-side and platform-agnostic.

If iOS ever needs its own AI-facing surface, `lib/coach-ai.ts` and
`lib/recommendation-safety.ts` (below) are the pattern to follow: gate
before the model call, ground the instructions in real data, sanitise after.

## 4. Also since `fad7644` — bugs, not features, worth knowing about

- **`discoverNearby()` had never once worked.** `(p.cell_x, p.cell_y) = any($2::record[])`
  is invalid Postgres — confirmed against the live database, not assumed —
  so it threw on every call and the route reported itself "temporarily
  unavailable." Fixed with `unnest()`. If iOS has its own retry/fallback
  logic around that specific error string, it can come out.
- **`deterministicSafetyRecommendation()` matched `member.goals` and
  `member.constraints`** against a clinical-language regex meant for acute,
  recent reports. `"Support hormonal or life-stage wellbeing"` — one of
  seven onboarding goal choices, aimed at this app's own stated demographic
  — matched on the word "hormonal" alone and permanently blocked every
  future AI recommendation for that member, since nothing anywhere ever
  resolves a `needs_coach_review` status. Now `lib/recommendation-safety.ts`
  only treats a pain-flagged workout log or a symptom in the last 7 days as
  acute. Two Today cards that used to scan the *entire* recommendation
  history for any match now read only the most recent one
  (`mobile/src/recommendations.ts`), so a single old flag can't haunt every
  day after it.
- **The join-code field was `autoCapitalize="characters"`**, force-uppercasing
  every keystroke, while the server compared case-sensitively. Fixed on both
  sides — field no longer mangles input, and the comparison is
  case-insensitive regardless.
